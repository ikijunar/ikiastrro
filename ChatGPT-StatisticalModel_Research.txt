
• For Ikiastrro, I would build a statistical layer on top of the existing classical rule engine—not replace it.

  Your current system already has useful foundations:

  - tbl_Rule_GrahaDignity and DignityScore
  - Shadbala and Bhava Bala calculators
  - Yoga evaluators and source-attributed yoga classifications
  - RuleSetId provenance
  - chart-level and planet-level fact tables
  - D1/D9/varga data
  - test fixtures and deterministic calculation outputs

  The statistical system should consume these as features and produce probabilities, calibrated scores, and explanations.

  ## 1. Define what “strength” means

  A model cannot learn “yoga strength” unless you define an observable target.

  Use separate targets:

   Concept            Possible target
  ━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Planet dignity     Expert-rated dignity level, or an outcome associated with the planet
  ─────────────────  ──────────────────────────────────────────────────────────────────────
   Planet strength    Shadbala/Bhava Bala category, expert assessment, or observed outcome
  ─────────────────  ──────────────────────────────────────────────────────────────────────
   Yoga strength      Manifestation probability, intensity, or outcome rating
  ─────────────────  ──────────────────────────────────────────────────────────────────────
   Timing             Whether the yoga manifests during a particular dasha/transit period

  Avoid one vague score such as YogaStrength = 82. Store:

  - score
  - probability
  - confidence interval
  - model version
  - feature explanation
  - rule-set version

  ## 3. Model planet dignity separately

  Start with an interpretable ordinal model.

  For example:

  DignityClass ∈ {VeryWeak, Weak, Neutral, Strong, VeryStrong}

  Potential approaches:

  - Ordinal logistic regression
  - Bayesian ordinal regression
  - Generalized additive model if you need nonlinear degree effects

  Input variables could include:

  - classical dignity category
  - continuous DignityScore
  - distance from exaltation/debilitation degree
  - Shadbala components
  - house placement
  - combustion
  - retrogression
  - vargottama
  - benefic/malefic aspects
  - D9 condition

  The model should not learn the same rule it is being asked to reproduce. If the target is simply the existing DignityScore, the model adds little value. A
  better target is an independently collected expert assessment or an outcome label.

  ## 4. Model planetary strength as a latent or composite construct

  Planet strength should not be represented as a simple sum of dignity and Shadbala unless that is explicitly your chosen classical definition.

  A useful first model is:

  PlanetStrengthProbability =
      f(Dignity,
        Shadbala,
        BhavaBala,
        house placement,
        aspects,
        conjunctions,
        varga support,
        combustion,
        retrogression)

  Use a hierarchical model:

  strength ~ planet + chart_type + dignity + shadbala + bhava_bala

  The planet effect matters because the same indicator may have different interpretive weight for Saturn, Jupiter, Moon, etc.

  A Bayesian hierarchical model is attractive because your data will probably be sparse and uneven across planets, signs, yogas, and life areas. It allows
  the model to share information while retaining planet-specific differences.

  ## 5. Model yoga strength as an interaction model

  Yoga strength is fundamentally interaction-heavy. It should include:

  1. Yoga presence
  2. Completeness of the classical conditions
  3. Strength of every required planet
  4. Dignity of those planets
  5. House support
  6. Affliction or cancellation
  7. Varga confirmation
  8. Dasha/transit activation
  9. Relevant life-area outcome

  A useful interpretable formula is:

  YogaEffect =
      YogaPresence
    × Completeness
    × RequiredPlanetStrength
    × HouseSupport
    × VargaSupport
    × TimingActivation
    × (1 - AfflictionPenalty)

  That formula is useful as a baseline, but I would not make it the final statistical model. Multiplication makes a zero or near-zero feature dominate
  everything.

  Better options:

  - Logistic regression for binary manifestation
  - Ordinal regression for weak/moderate/strong manifestation
  - Gradient-boosted trees for predictive performance
  - Bayesian hierarchical logistic regression for sparse, interpretable data
  - Generalized additive models for nonlinear strength curves

  Use the multiplicative score only as an explainable baseline against which more advanced models can be compared.

  ## 6. Treat the three concepts as a hierarchy

  The cleanest conceptual model is:

  Dignity
     ↓
  Planetary strength
     ↓
  Yoga strength
     ↓
  Timed manifestation
     ↓
  Observed outcome

  In statistical terms:

  DignityScore → PlanetStrength → YogaStrength → Outcome

  This is preferable to training three unrelated models because it reflects your domain structure.

  A practical first version could be:

  PlanetStrength = model_1(features)
  YogaStrength = model_2(yoga_features, PlanetStrength)
  ManifestationProbability = model_3(yoga_features, PlanetStrength, timing_features)

  Later, this can become one Bayesian hierarchical model.

  ## 7. Collect outcomes independently

  This is the most important part.

  If you train on Ikiastrro’s own calculated dignity and yoga labels, the model will mostly rediscover your rules. That may be useful for consistency
  checking, but it is not evidence that the yoga predicts real-world outcomes.

  You need outcome observations such as:

  ChartResultId
  LifeAreaCode
  OutcomeCode
  OutcomeRating
  OutcomeDate
  OutcomeSource
  OutcomeConfidence
  DashaPeriod
  TransitContext
  ObserverId

  Examples:

  - Career promotion during a relevant dasha
  - Marriage event
  - Educational achievement
  - Financial improvement
  - Health event
  - Public recognition
  - Relocation
  - Spiritual practice milestone

  Use a defined rating scale, for example:

  0 = absent
  1 = weak
  2 = moderate
  3 = strong
  4 = exceptional

  Record the source and confidence of every observation. Separate self-reported, expert-rated, and externally verified outcomes.

  ## 8. Avoid common statistical traps

  Astrology data will be especially vulnerable to these problems:

  ### Data leakage

  Do not allow future outcomes, later dashas, or post-event annotations into features used to predict the event.

  ### Small samples

  A model for 100 yogas and 9 planets requires far more data than a few hundred charts. Begin with a small number of high-quality yogas.

  ### Class imbalance

  Strong manifestations may be rare. Use precision/recall, PR-AUC, calibration, and confidence intervals—not accuracy alone.

  ### Correlated features

  Dignity, Shadbala, Vargottama, and several classical strength measures may encode overlapping information. Check feature correlation and use
  regularization.

  ### Multiple testing

  If you test hundreds of yogas against many outcomes, some apparent relationships will occur by chance. Use held-out validation and pre-register the
  hypotheses you intend to test.

  ### Selection bias

  Charts submitted to an astrology application are not a random sample of the population. Record the source population and avoid claiming general population
  validity.

  ### Circular validation

  Do not validate yoga strength against an expert score that was itself derived from the same yoga rules. Keep rule-derived labels and independent outcomes
  separate.

  ## 9. Recommended technology for Ikiastrro

  I would use a two-stage architecture.

  ### Training

  Use a separate Python training project for:

  - pandas or Polars
  - scikit-learn
  - statsmodels
  - PyMC or Bambi for Bayesian models
  - SHAP or permutation importance
  - MLflow or a simple model registry

  Python is currently better suited to Bayesian modeling, calibration, and statistical diagnostics than ML.NET.

  ### Production inference

  Keep inference inside the .NET application:

  - Export simple models as coefficients and evaluate in Core
  - Export tree models to ONNX and run with Microsoft.ML.OnnxRuntime
  - Store model metadata and feature definitions in SQL Server
  - Keep training offline and predictions deterministic for a given model version

  Suggested project structure:

  src/Ikiastrro.Core/Statistics/
    Features/
    Models/
    Predictions/
    Calibration/

  src/Ikiastrro.Data/Statistics/
    StatisticalFeatureRepository.cs
    StatisticalModelRepository.cs
    PredictionRepository.cs

  research/statistical-models/
    notebooks/
    training/
    evaluation/
    exports/

  Do not put Python execution inside the Blazor request path.

  ## 10. Suggested implementation sequence

  ### Phase 1: Feature store

  Build deterministic SQL projections for planet and yoga features. Add feature snapshot tests.

  ### Phase 2: Descriptive analytics

  Before machine learning, calculate:

  - frequency of each yoga
  - average dignity by planet
  - outcome rates by yoga
  - outcome rates by strength bucket
  - confidence intervals
  - missing-data rates

  This will reveal whether modeling is justified.

  ### Phase 3: Baseline models

  Implement:

  - ordinal logistic regression for dignity
  - regularized logistic regression for yoga manifestation
  - calibrated probability outputs
  - train/validation/test splits by person or chart family

  ### Phase 4: Hierarchical model

  Introduce planet-, yoga-, source-, and life-area-level effects. This is likely the most statistically appropriate model for Ikiastrro.

  ### Phase 5: Timing model

  Add Dasha and transit context only after the static chart model is stable.

  ### Phase 6: UI presentation

  Show:

  Yoga strength: Moderate
  Manifestation probability: 0.64
  Confidence: Wide
  Main supports: Jupiter dignity, D9 confirmation
  Main weakness: Saturn affliction
  Activated during: Jupiter/Saturn period
  Model: YogaStrength v0.3

  Users should be able to inspect why a score was produced.

  ## My recommended first model

  Start with one carefully chosen yoga and one outcome category.

  For example:

  Target:
    Strong career manifestation during a relevant dasha

  Features:
    yoga presence
    completeness ratio
    required planet dignity
    required planet Shadbala ratio
    10th-house support
    10th lord strength
    D9 confirmation
    benefic aspects
    malefic affliction
    dasha activation

  Train three baselines:

  1. Rule-based weighted score
  2. Regularized logistic regression
  3. Bayesian hierarchical logistic regression

  Compare:

  - calibration
  - out-of-sample log loss
  - precision/recall
  - feature stability
  - expert interpretability

  If the statistical model cannot outperform the transparent rule baseline on held-out data, keep the rule baseline.

  The key design principle is: classical astrology remains the feature and provenance layer; statistics estimates uncertainty, relative strength, and
  outcome association. That gives Ikiastrro a defensible “why this score?” story without pretending that a model has established causal truth.
